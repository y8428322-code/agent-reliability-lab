## 3. 三个结论

### 3.1 当前最突出的失败模式是「**做多了**」，不是「忘了做」

**所有 8 次失败中有 7 次是"多执行了一个写操作"**：

| 失败 | 实际多做了什么 |
|---|---|
| A_native / T01 | 建了 **2 个**工单（断网 + 电视信号），gold 只要求 1 个 |
| A_native / T03 | 用户只要求换机，额外建了一个故障工单 |
| A_native / H2 | 额外建了一个故障工单（gold 只要求换机） |
| **全部变体 / H9** | 用户同时说"断了"+"要换机"，agent 把两件都办了；策略要求一次只办一件 |

**没有一次失败是"该做的没做"。** 这与第一轮（6 条简单任务、DB 全对）的印象完全相反——
**任务变难之后，暴露出来的不是能力不足，而是行为边界感缺失。**

### 3.2 原生 function calling 反而**更差**（0.750 / 0.812 vs 0.938）

反直觉但数据一致。原生模式下模型会**把用户话里的每个诉求都执行一遍**：

- T01：用户提了"宽带断了 + 电视看不了" → 原生模式建了 2 个工单；文本式只建 1 个。
- T03：用户只提换机 → 原生模式顺手建了故障单；文本式不建。

**假设**：原生模式把 tool_calls 直接交给模型自主决定，模型的"待办清单"被完整执行；
而文本式模式要求模型把调用写成 `<tool_call>` 文本，这个**额外的序列化步骤**起到了
"再检查一遍"的作用，抑制了多余动作。

> 这条结论要谨慎解读：只有 1 个模型、1 个域、1 次试验，**不能外推**。但它足以说明
> "换成更现代的调用协议 ≠ 更好"，值得在更大样本上验证。

### 3.3 反思闭环（C）对本任务集**没有效果**，而且原因很明确

`C_reflection` 在 H9 上和基线一样失败。原因不是实现问题，而是**方法本身的盲区**：

> Reflexion 式反思记忆是**"待办清单"**性质的：它问的是"还有什么没做"，
> 因此天然偏向**补做**。而本任务集的主要失败是**做多了**——
> 反思里没有"你已经多做了一步"这个概念，自然无从纠正。

这是本轮最有方法论价值的一条：**评估一个改进手段之前，先确认失败模式与该手段的作用方向是否匹配。**
如果主失败模式是"过度执行"，需要的是**减法机制**（动作合理性校验、工具描述里写明
"未被明确要求时不要调用本工具"、把"一次只做一件事"提到工具级约束），而不是补做清单。

### 3.4 上下文工程（B）在文本式下**正确率无变化**，但工具调用更少

- pass@1：0.938 = 0.938（无差异）
- 平均工具调用：3.4 → **3.2**（少 6%）
- 在原生模式下：B_native 0.812 vs A_native 0.750（**反而更好**，+2 个任务）

有意思的一点：**上下文工程在原生模式下才体现出正确率收益**（+0.062），
在文本式下没有。原因与 3.2 相同——原生模式缺少"序列化自检"，更需要显式的规则约束来兜底。

## 4. NL 断言维度**完全无区分度**（全部 1.000）

所有失败都是 DB 层面的"多写/少写"，而不是"没说清"。当前 NL 断言设计偏易：

- T01/T03/H2/H9 的失败，agent 其实**都**告知了工单号和时效 → NL 判定通过是**正确的**
- 真正的违规（多建一个工单）在自然语言里**看不出来**

**改进方向**（Phase 3）：
1. 加"**不得声称已完成未做的事**"类断言（如"回复中没有声称已更换设备"）
2. 对"多写"类失败，用**动作合理性断言**而不是文本断言
3. 引入**动作级校验器**：把工具调用序列与策略规则做模式匹配（例如"建单后不应再出现同客户同故障类型的第二次建单"）

## 6. 局限（复述，防过度解读）

1. **1 个模型、1 个域、每个任务只跑 1 次** → 没有置信区间，0.062 的差距**可能是噪声**
2. **用户是脚本化的** → 不测"应对混乱用户"
3. **NL 维度无区分度** → 当前有效的判分只有 DB 维度
4. **无外部分数对照** → 只做组内消融，不宣称绝对水平
5. 任务是自写的 → 判分逻辑与 agent 实现完全解耦（gold 由参考轨迹独立回放得出）
