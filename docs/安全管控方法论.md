# 安全管控方法论

> 本文只写**方法、步骤与原理**，本次不做任何复现实现。
> 核心来源：**腾讯朱雀实验室 A.I.G（AI-Infra-Guard）**，辅以 Claw-Eval 的安全评测结论。

---

## 0. 先澄清一件事：朱雀实验室有两个不同的东西

用户原始描述里的"腾讯朱雀实验室的 AIG"指的是 **AI-Infra-Guard（A.I.G）**，即**AI 红队扫描平台**——它防的是"agent 自身被攻击"。而朱雀实验室另有一个 **AIGC 内容检测**服务（https://matrix.tencent.com/ai-detect），它做的是"这段文字/图片是不是 AI 生成的"。

**两者用途完全不同，不要混用**：

| | A.I.G / AI-Infra-Guard | 朱雀 AIGC 检测 |
|---|---|---|
| 保护对象 | agent / MCP / AI 基础设施 | agent **产出**的内容 |
| 回答的问题 | "这个 agent 会不会被攻破？" | "这段话是不是 AI 写的？" |
| 形态 | 开源红队平台，7,236★，Apache-2.0，Python | 在线服务 + 第三方 CLI 封装 |
| 本文位置 | 第 1、3、4 节 | 第 2 节 |

---

## 1. A.I.G（AI-Infra-Guard）：全栈 AI 红队平台

### 1.1 定位与形态

- 仓库：https://github.com/Tencent/AI-Infra-Guard （**7,236★，Apache-2.0，Python**，2026-10-30 仍在推送）
- 官方描述：*"A full-stack AI Red Teaming platform securing AI ecosystems via **Agent Scan, Skills Scan, MCP scan, AI Infra scan and LLM jailbreak evaluation**."*
- 交付形态：Docker 镜像 `zhuquelab/aig-server`，另有 ClawHub 上的 `aig-scanner` / `edgeone-skill-scanner` / `edgeone-clawscan` 组件。
- 官方文档：https://tencent.github.io/AI-Infra-Guard/

### 1.2 五类扫描器：各自原理

| 扫描器 | 检测对象 | 原理 | 对应风险 |
|---|---|---|---|
| **Agent Scan** | agent 的提示词 / 系统提示 / 工具声明 | **静态分析 + 规则匹配**：扫描是否存在指令覆盖、角色劫持、危险工具无确认、敏感信息外发 | 提示注入、越权 |
| **Skills Scan** | Skill / 插件包 | 对 skill 的声明、脚本、安装钩子做供应链式审计：安装期即执行的命令、外发网络请求 | 插件投毒 |
| **MCP Scan** | MCP server 配置与 tool schema | 检查 MCP server 来源、tool description 中是否夹带指令（**tool description 注入是 MCP 特有的攻击面**）、server 是否暴露本地命令执行 | MCP 投毒 |
| **AI Infra Scan** | 部署面 | 端口暴露与鉴权检查（例如 Ollama 无鉴权监听在 `0.0.0.0:11434`）、密钥硬编码、危险默认配置 | 基础设施裸奔 |
| **LLM Jailbreak Evaluation** | 模型端点 | 用攻击语料库对目标端点做**对抗测试**，统计越狱成功率 | 模型越狱 |

> 公开报道中 A.I.G 覆盖的典型场景：Ollama 裸奔、MCP 投毒、Agent 越权、模型越狱。

### 1.3 方法步骤

1. **部署**：`docker run zhuquelab/aig-server`，或用 ClawHub 组件按需装单个扫描器。
2. **选扫描器**：按暴露面选（agent 提示词 → Agent Scan；MCP 配置 → MCP Scan；服务端口 → AI Infra Scan；模型服务 → Jailbreak Evaluation）。
3. **配置目标**：指向本机 agent 工程目录、MCP server 配置、或模型端点 URL + 凭据。
4. **执行扫描**，产出风险项清单（按严重等级分级）。
5. **修复并复扫**，形成基线（把扫描报告纳入 CI，防止回归）。
6. 对 Jailbreak Evaluation，额外维护一份**攻击语料集**，每次换模型/换 Prompt 都重跑，比较越狱成功率变化。

### 1.4 局限

- 静态扫描只能发现**已知模式**的注入与越权，对语义级的社工攻击无能为力——必须配合第 4 节的运行时审计。
- 官方定位是**红队**（找漏洞），不是**护栏**（运行时拦截）。运行时拦截要自己接第 3 节的三道关。

## 2. 朱雀 AIGC 内容检测（针对产出内容）

### 2.1 原理

| 模态 | 原理 | 说明 |
|---|---|---|
| 文本 | **判别器 + 统计特征**（困惑度分布、句长方差、标点与用词指纹） | 生成文本的困惑度通常偏低且方差小；标点分布、用词多样性有统计特征差异 |
| 图片 | **频域伪影 / 频谱特征** | 生成模型（扩散模型等）在频域留下可辨识指纹；朱雀实验室另有 ICML 2025 Spotlight 的傅里叶分解工作提升泛化 |

### 2.2 形态

- 在线：https://matrix.tencent.com/ai-detect （文本 + 图片）
- 第三方 CLI 封装（非官方）：`Sophomoresty/zhuque`、`skystmm/zhuque-ai-detector` 等，调用同一服务并做批量/串行调度。

### 2.3 方法步骤（用于对外产出物的合规自查）

1. 把要对外发布的文本/图片提交检测。
2. 读取「AI 生成概率 / 判定结论」。
3. 阈值判定：超过团队自定阈值则触发人工改写流程（调整句式、增加具体细节、改变段落结构）。
4. 把检测结果**作为一条独立评测维度**记录下来，而不是阻塞式拒答——目的是"降低 AIGC 率"，不是"禁止生成"。

### 2.4 注意

- **检测器会误判**：短文本、模板化公文、代码注释都容易被判为 AI 产出。
- **在线服务 = 把内容传出**：涉密文本不能提交。在线判定是"合规避让"，不是"内容安全"。

## 3. Agent 输出的三道关（可离线落地，不依赖上述平台）

这是把上面的思想落成本项目可直接实现的形式。

### 关一：输入侧（进入模型之前）

- **提示注入识别**：对用户输入 + 检索到的知识片段做检测，识别"忽略以上指令""你现在是…"等模式。
- **知识消毒**：RAG 检索到的文档是提示注入的**经典载体**——外部文档里的指令会被模型当作上级指令执行。检索结果必须当作**不可信数据**处理（加边界标记、降权、或单独通道传入）。
- **越权意图识别**：用户是否在诱导调用不该调用的工具。

### 关二：工具侧（模型想动手时）

- **白名单**：只有显式注册的 `function_list` 里的工具可被调用；未注册工具名直接拒绝，不给模型"协商"的机会。
- **参数强校验**：类型、范围、路径前缀、长度上限；写操作与外发操作需要二次确认。
- **危险操作分级**：只读（查询）可自动执行；写盘、发网络、执行命令需要显式确认或沙箱。
- **副作用最小化**：工具实现里不接收任意路径/任意 URL；沙箱化。

### 关三：输出侧（模型答完之后）

- **敏感信息外泄扫描**：密钥、token、内网地址、个人信息是否被回显。
- **内容合规检查**：结合第 2 节的 AIGC 检测（对外产出物场景）。
- **轨迹审计**：检查整条工具轨迹有没有出现越权动作——这一步**不能省**，理由见第 4 节。

## 4. 安全必须做成「评测维度」，而不是只做「拒答」

Claw-Eval 对 300 个人工校验任务的公开分析指出：**44% 的安全违规被漏检**。

漏检的根因是——**违规发生在中间的���具调用里，而最终回答看起来完全正常**。例如 agent 被诱导调用了"删除文件"或"把数据 POST 到外部地址"，但最后回答只是"已完成"。

因此安全评测的正确形态是：

1. 审计**整条轨迹**（工具名、参数、返回值），而不是只看最终回答。
2. 安全作为**打分维度**与完成度并列（对应 Claw-Eval 的 Completion / Safety / Robustness 三维）。
3. 判定标准用 **Pass^3 口径**：同一任务连跑 3 次，3 次都不出现越权动作才判安全通过——偶发一次"没出事"是运气，不是能力。

落到 OpenJudge 的 grader 体系里，`Tool Selection` / `Tool Parameter Check` / `Trajectory` 这几个 grader 就是干这件事的；安全规则则写成**自定义 grader**（有明确规则 → 用 Python 接口直接实现，不要交给 LLM 自由裁量）。

## 5. 在本项目（Qwen-Agent + MiniMax）的具体落点

### 5.1 已经天然成立的部分

- **工具白名单**：`Assistant(function_list=[...])` 只暴露显式注册的 `BaseTool` 实例；上游 `_init_tool` 对未注册名直接 `raise ValueError('Tool X is not registered.')`。白名单是框架自带的。
- **参数校验**：上游 `BaseTool._verify_json_format_args()` 已做必填校验与 JSON Schema 校验（`jsonschema`），我们可直接扩展为更严格的 schema。

### 5.2 需要自己加的位置

| 关卡 | 插入点（基于上游源码） | 做法 |
|---|---|---|
| 输入过滤 | `Assistant.run()` 之前 | 对 `messages` 做注入检测；对 RAG 知识片段加不可信边界标记 |
| 工具执行 | `qwen_agent/agent.py::_call_tool()` 前后 | 执行前做参数强校验；执行后扫描返回值是否含敏感信息 |
| 输出过滤 | `Assistant.run()` 之后 | 扫描最终 `content` |
| 轨迹审计 | 收集消息序列中 `role == 'function'` 的条目 | 按 rubric 逐条判定；这是安全评测的**唯一可靠数据源** |

### 5.3 本项目当前配置下的具体风险清单

| 风险 | 说明 | 建议 |
|---|---|---|
| **内置 `code_interpreter` 工具** | 上游示例普遍挂载，能执行任意代码 | 本项目**不挂载**；生产化时若需要，必须进沙箱 |
| **RAG 知识注入** | 检索片段被当作指令执行 | 知识片段消毒 + 边界标记 |
| **GroupChat 自动路由** | 用户输入会被转述给其他 agent，注入面放大 | 只在受信场景启用；对外场景关掉 `group_chat` |
| **密钥落在 `~/.claude/settings.json` 明文** | 本机 `sk-cp-` key 直接可读 | 不写入任何入库文件；用环境变量注入；必要时改用只读子 key |
| **模型端点无 per-tool 鉴权** | 模型可调用白名单内**任意**工具 | 工具侧按"危险度"分级，写操作单独确认 |

## 6. 后续实施建议（进入下一阶段再做）

1. 先做**关二**（工具白名单 + 参数强校验），因为改动最小、收益最直接。
2. 再做**轨迹审计**，把安全维度并入 L3 评测层（见 `评测与调优方法论.md` 第 4 节）。
3. 需要更强的扫描能力时，再引入 A.I.G 做**红队侧**的定期体检（尤其在接入 MCP 或新增 skill 时）。
4. 对外产出物多的场景，再接朱雀 AIGC 检测做内容合规自查。
