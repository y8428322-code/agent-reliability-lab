# 实验报告 v8：机制约束（工具层）—— 第一次真正动到工具层

- 日期：2026-11-02
- 模型：MiniMax-M3.1-Flash ｜ 框架：Qwen-Agent（上游 commit `31a4d36`，未魔改）
- 域：`telecom_cn`（17 任务）｜ 数据：3 变体 × 51 次 = **153 次运行，0 次中断**
- 对照设计：`B_guard` 与 `B_crop_keepredline` 的**策略文本完全相同**，只差工具层的机制约束

---

## 1. 出发点

v7 得出两条结论：

1. 「一次只办一件事」写成**文字禁令**会被 agent 读成"别多做事"→ 从"过度执行"翻转成"该做不做"（H7 上 tools=0）
2. 但 H9 的 12 次失败**全部**是「同一回合内连续执行 建单 + 换机」（tools=7~9）

于是本轮的做法是：**把这个约束从 prompt 挪到工具层** —— 第二���写操作直接被工具挡住，
并返回一句可转述给用户的话。这是「**收紧可行域**」而不是「**增加禁令**」。

实现：`domain/tools.py: TurnGuard`，同一回合只准一次写操作；runner 每回合 `begin_turn()` 重置。

## 3. 三个结论

### 3.1 **机制约束有效**：这是本项目第一次证明「改工具层」比「改 prompt」更管用

| | pass^3 | 配对 |
|---|---|---|
| `B_crop_keepredline`（只有文字约束） | 0.824 | — |
| `B_guard`（+ 工具层机制约束） | **0.941** | **2 : 0** |

**同一份策略文本、只差工具层的一个守卫**，pass^3 提升 **+0.117**，配对 **2:0**（H5、H10 各从 2/3 升到 3/3）。

> 对照 v7 的教训：同一件事，
> **写成 prompt 里的禁令 → 让 agent 畏首畏尾**；
> **写成工具层的拦截 → 让 agent 做该做的、但做不了不该做的**。
> 区别不在措辞，在**约束落在哪一层**。

### 3.2 但 H9 仍然全灭 —— 机制守卫的**边界被精确定位**了

守卫确实触发了（轨迹里能看到拒绝消息），但**没挡住**：

```
t2: create_repair_ticket 成功        ← 业务 A（报修）
    check_device_warranty / list_inventory
    replace_device → 拒绝：「本回合已办理「create_repair_ticket」…」
    replace_device → 拒绝…
    ...
t3: 第 2 回合 → guard.begin_turn() 重置 → replace_device 成功   ← 业务 B（换机）过了
```

**根因**：守卫是**每回合重置**的，而 H9 的过度执行是**跨回合**的 ——
第 1 回合办完第一个诉求，第 2 回合用户说「好的麻烦快些」，agent 就去办第二个诉求。

**这不是实现 bug，是机制设计的边界**：「同一回合一次写操作」能压住**冲动型**过度执行，
压不住**分回合推进型**过度执行。后者需要判断「用户是否单独确认了第二件事」——
这在自然语言里比「同一回合」微妙得多。

### 3.3 守卫的拒绝消息**不够强**，导致 agent 反复重试

`B_guard` 的 3 次失败**全部**是「参数错」——轨迹显示 agent 被挡后**在同��合里连续重试 3~4 次**
同一��被拒的工具：

```
replace_device → 拒绝：「本回合已办理「create_repair_ticket」…」
replace_device → 拒绝…
replace_device → 拒绝…
```

拒绝消息说的是「请先向用户说明并获得用户确认后再操作」，但 agent 把它当成**可重试的错误**
（正好撞上 R17「工具报错就纠正参数后重试」那条规则）→ 于是陷入重试循环。

> **机制约束的拒绝消息必须与「工具错误」在语义上区分开**：
> 工具错误 = "你的参数错了，改一下再来"；机制拒绝 = "这条路现在不通，换个做法"。
> 否则 agent 会把它当参数错误一路重试。

## 4. 下一步（基于本轮结论）

| 优先级 | 动作 | 评判标准 |
|---|---|---|
| **P0** | 守卫的拒绝消息改成**不可重试**语义（例如「本回合不受理其它业务；请先与用户确认后，在下一轮办理」），并让 agent 知道这是终止性拒绝 | `B_guard` 的「参数错」归因归零 |
| **P0** | 守卫升级为**跨回合**版本：办理业务 B 时要求「用户在本轮单独提到过 B」——用业务关键词匹配用户消息 | H9 从 0/3 转为通过，且 H2（只提一个业务、下一轮才办）**不受影响** |
| P1 | 把「多诉求 → 第二个需用户单独确认」写进**判分口径**（gold 与断言对齐） | gold 可推导性 100% |
| P1 | 长度扫描（445/700/1000/1547/全量） | 找出收益拐点 |
| P2 | 扩任务到 30 条 + 第二个域 | 最小可分辨差异 ≤0.033 |

### 4.1 「跨回合守卫」的设计草案（下一步要实现的东西）

规则：**每个写操作业务名，在一个会话内**——
- 该业务**在用户某轮消息里被明确提到过**，且**提到它的那一轮之后用户没有再单独确认它** → 拒绝
- 用户在**最近一轮**单独提到了它 → 放行（视为用户确认）

业务关键词映射（示例）：

| 业务 | 用户可能用的说法 |
|---|---|
| 报修工单 | 报修、维修、派人上门、坏了修一下 |
| 设备更换 | 换机、换一台、更换设备 |
| 退款 | 退款、退钱、退我 |
| 工单撤销 | 撤单、取消工单 |

**为什么这个设计能同时满足 H2 和 H9**：
- H2：用户 turn1 只提「换机」→ 换机已被提出且无第二业务 → turn2 办理放行 ✓
- H9：用户 turn1 同时提「报修」和「换机」→ 两者都需单独确认 → turn2 用户说「好的麻烦快些」（未单独确认换机）→ 换机被挡 ✓；若 turn3 用户说「对，那就换吧」→ 放行 ✓
