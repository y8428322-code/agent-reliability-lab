# 实验方法与评判标准

> 本文档说明这套评测床**怎么判分、怎么保证结论可信、以及每一步开工前要检查什么**。
> 判分口径、实验规范与评判标准都写在这里，任何一轮实验的数字都应当能对照本文复核。

---

## 1. 判分口径

### 1.1 DB 维度：比对终态哈希，不比对调用序列

参考 [τ²-bench](https://github.com/sierra-research/tau2-bench) 的做法：

```
参考轨迹 ──回放到干净 DB──> 目标终态 ──哈希──┐
                                              ├─ 相等 → 通过
agent 写操作 ──发生在同一份 DB──> 预测终态 ──哈希─┘
```

**要点**：任何产生等价终态的调用序列都算通过，不要求调用顺序一致。

**哈希的计算**：对状态做规范化后取 `sha256`：

- `customers` / `devices` / `inventory`：字典，键排序
- `tickets`：按 `[customer_id, fault_type, status, created_at]` 排序的列表 —— **剔除自动分配的工单号**
- `refunds`：按 `[customer_id, amount, status]` 排序的列表 —— 剔除自动分配的退款号

剔除自动 id 是必要的：工单号按创建顺序分配，如果 agent 与参考轨迹以不同顺序创建同样的工单，
按 id 比较会把它们判成不一致。剔除后仍能检出**重复创建**（列表保留重复项）。

### 1.2 NL 维度：模型判定 + 可机械核对的交叉验证

判分方式：把完整对话轨迹交给模型，逐条判断断言是否满足。

判定器的可靠性是**被验证过的**，不是假设的：

| 验证方式 | 结果 |
|---|---|
| 否定式断言的构造样例（声称做了 vs 没做） | 4/4 正确 |
| 与确定性正则交叉核验（工单号 / 24 小时 / 金额 / 欠费 / 过保 / 序列号） | **255/255 一致** |

### 1.3 奖励 = DB 维度 × NL 维度

两个维度都通过才算通过。归因时按下面的优先级给出**可定位的原因**：

| 归因 | 含义 |
|---|---|
| `状态不符(多建单 x1)` | 相对目标终态多了一次写操作 |
| `状态不符(少建单 x1)` | 该做的写操作没做 |
| `状态不符(换机参数不符)` | 做了但选错了目标（如换机选错型号） |
| `工具调用格式错误` | 模型写了 tool_call 但标签损坏，工具没执行 |
| `机制拒绝` | 被工具层的机制约束挡下 |
| `参数错` | 工具返回参数错误 |
| `未闭环` | 状态对，但回复没把关键信息说清 |

## 2. 实验规范

### 2.1 判分器自身要先被检验

在用判分器评价 agent 之前，先验证判分器：

| 检验 | 做法 | 通过线 |
|---|---|---|
| **灵敏度**（变异测试） | 对每个任务的参考轨迹造一个**单点错误**（改故障类型 / 换错库存序列号 / 改退款金额 / 多加一张单），判分器必须全部拒绝 | 全部拒绝 |
| **判定器可靠性** | 对否定式断言构造「声称做了」与「确实没做」的样例 | 与人工判断一致 |
| **独立第二意见** | 用确定性正则独立核验可机械判定的断言 | 与模型判定一致率 ≥90% |

### 2.2 gold 必须能由策略推出

每条任务的参考轨迹，都要能对照策略里的某条规则推导出来。
**凡是策略里没规定的事，任务就不该去判**。

配套要求：**策略与任务双向一致** —— 策略里有的规则要有任务覆盖，任务里的 gold 要有策略依据。

### 2.3 一个变体只差一个变量

拆解实验时，每个变体之间只允许有一个开关不同（上下文组织方式 / 规则集版本 / 机制约束）。

为此，规则集按版本分开存放，变体显式绑定：

| 文件 | 用途 |
|---|---|
| `domain/policy_rules_legacy.yaml` | 基线规则集 |
| `domain/policy_rules_v1.yaml` | 规则集对照条件之一 |
| `domain/policy_rules.yaml` | 当前规则集 |

> 一个常见的坑：同时改规则集和渲染策略，会让两者的效应混在一起。
> 本项目因此把"规则集版本"做成显式的变体维度。

### 2.4 效应量必须大于批次间噪声

**这是本项目最重要的一条实验规范。**

同一配置、同一规则集，跑多个独立批次，结果会有波动：

| 指标 | 批次间 σ | 说明 |
|---|---|---|
| pass@1 | **≈ 0.015** | 相对稳定 |
| **pass^3** | **≈ 0.044** | 对边界任务的单次翻转格外敏感 |

**由此得出的规范**：

1. 每个配置至少 **3 个独立批次**，合并后按任务算 pass^3
2. 效应量判定以 **pass@1 + 配对检验**为主，pass^3 只作参考
3. 结论门槛：效应量需 **> 2σ（约 0.09）**，否则只表述为"未观察到显著差异"
4. **优先报配对差异**（同一任务上逐对比，粒度 = 1 个任务），它比总体 pass^3 灵敏
5. 任何小于 1/任务数（约 0.059）的比例阈值**没有统计意义**

### 2.5 判分标准要跑前写死

每轮实验开始前，先把"什么算成功"写成可判定的条目，跑完只对着它核销。
这样能避免"结果出来后回头找说法"。

已用过的判分标准示例：

- 安全裁剪实验：`B_crop_safe` 的 pass^3 应 ≥ `B_points`；「多做」类失败应归零
- 规则集实验：规则集改动后 pass@1 与 pass^3 都不低于基线；**零工具调用数不上升**；
  若不成立则区分原因（规则内容问题 vs 措辞边界问题）

### 2.6 基础设施故障与模型失败分开统计

请求被限流、超时等导致的中断，**不是模型答错**，必须单独标记并从正确率里剔除，
否则一次限流就能把整轮结论带偏。

实现上：指数退避重试 + 中断标记 `aborted` + 统计时排除并单独报告。

### 2.7 统计量要看中位数

工具调用次数的**均值**会被个别失控运行拉偏，因此工具调用一律看中位数。

### 2.8 过程指标与成败指标分开看

只看最终通过率，会漏掉一类退化：**agent 变得畏首畏尾，什么都不做**。

本项目为此加了独立于成败的过程指标：

| 指标 | 含义 |
|---|---|
| `format_error` | 模型写了 tool_call 但标签损坏（未闭合 / 含零宽字符），工具没执行 |
| `deferred_no_action` | 回复里承诺「我先查 / 我这就办」，但该回合零工具调用 |
| `runaway` | 单轮工具调用数异常膨胀（模型陷入重复生成） |

### 2.9 规则的边界要划清

规则的风险不在"说了什么"，而在"管到哪里"：

| 规则形态 | 风险 |
|---|---|
| **被截断** | 模型只看到前半句，误以为自己有权限 |
| **边界模糊** | 模型把"还没开始"当成"没完成"，于是干脆不动 |

第二种更隐蔽 —— 规则读起来完全正确，也过了人工 review，只有跑起来才暴露。

**可操作的做法**：

1. 规则要写明它约束的是**「已失败的操作」**还是**「尚未开始的动作」**
2. 改完规则要跑多批次，并同时看 `deferred_no_action` 这类过程指标
3. 新增规则时，检查它是否可能被读成"什么都别做"

## 3. 每一步开工前的检查清单

1. **判分逻辑**：参考轨迹回放是否平凡通过？故意构造的错误是否必然失败？
2. **gold**：每条是否都能由策略推出？策略与 gold 是否双向一致？
3. **变体**：每级是否只差一个变量？有没有隐式差异（上下文长度、全局状态、随机性）？
4. **指标**：pass^k 公式与聚合方式是否正确？有没有被离群值污染？
5. **失败归因**：标签是否覆盖全部失败类型？有没有"结果对但原因错"？
6. **判分器本身**：有没有独立第二意见？人工核查覆盖了多少？
7. **意义性**：这轮实验能支撑什么结论、不能支撑什么？有没有被过度解读？
8. **遗漏细节**：有没有"看起来对其实错"的失败类型？有没有静默失败？
9. **规则改动**：新规则的边界划清了吗？会不会被读成"什么都别做"？

## 4. 当前结果的自评

| # | 标准 | 阈值 | 实测 | 结论 |
|---|---|---|---|---|
| 1 | 判分准确率（人工核查失败运行是否判对） | ≥95% | **100%**（20/20 逐条核对） | ✅ |
| 2 | 归因准确率 | ≥90% | **100%**（20/20） | ✅ |
| 3 | 判定器可靠性（否定式断言） | 100% | **100%**（4/4 构造样例） | ✅ |
| 4 | 判分器与确定性核验一致率 | ≥90% | **100%**（255/255） | ✅ |
| 5 | 判分器灵敏度（变异测试） | 全部拒绝 | **9/9** | ✅ |
| 6 | gold 可推导性 | 100% | **100%** | ✅ |
| 7 | 变体隔离 | 严格成立 | 逐对核对成立 | ✅ |
| 8 | 重复性（高分变体 pass^3 ≈ pass@1） | 接近 | 0.941 = 0.941 | ✅ |
| 9 | 失控率 | 0 | **0** | ✅ |
| 10 | 判定异常率 | <1% | **0** | ✅ |
| 11 | 规则集版本一致性（历史批次可合并） | 完全一致 | 11 个引用批次指纹一致 | ✅ |
| 12 | 格式错误率（上游 tool_call 标签损坏） | 监控 | 1.6% | ⚠ 上游缺陷，已记录并规避 |
| 13 | 任务区分度 | ≥8/17 | **5/17** | ❌ 偏低，需扩任务 |
| 14 | 判分独立第二意见（LLM 评审交叉） | ≥90% | 尚未做 | ❌ 待补 |

### 4.1 关于第 11 项

历史批次能否合并，取决于**它们运行时用的规则集是否一致**。本项目按提交时间逐批核对过规则集指纹，
被引用作结论的 11 个批次指纹完全一致；早期批次（规则集不同）只作历史留存，不参与结论。

同理，判分逻辑调整后，历史数据用新旧两种逻辑重算过一遍，判定结论没有变化，因此不需要重跑模型。

### 4.2 关于第 13 项

17 条任务里只有 5 条能区分变体，其余 12 条所有变体都是满分 —— 这类任务不提供信息量。
按当前失败归因反推，还缺这几类：

- **规则检索类**（规则埋在长文本里，测能不能检索到并应用）
- **跨条款交互类**（两条规则同时触发，要判断优先级）—— 目前完全没有
- **边界类**（恰好在阈值上 / 下）
- **信息不全需澄清类**
