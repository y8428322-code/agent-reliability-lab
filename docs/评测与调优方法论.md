## 1. Reflexion —— 用语言做强化学习

### 1.1 原理

Reflexion 把强化学习的三要素（actor / reward / policy update）替换成**纯语言版本**：

- **Actor**：执行任务的 LLM，产出推理轨迹与动作。
- **Evaluator**：判定本次尝试成功与否，给出标量反馈（0/1 或连续分数）。
- **Self-Reflection**：当反馈判定为失败时，让同一个 LLM 对自己的轨迹写一段**自然语言反思**，指出哪里错了、应该怎么改。
- **关键点**：反思**不更新模型参数**。它被写进一个**记忆缓冲区**，下一轮尝试时作为额外上下文拼进 prompt。

因此它可以在**不训练、只调用 API** 的前提下获得类似 RL 的改进效果——这正是它适合被"魔改"进我们项目的原因。

### 1.2 记忆结构

- 缓冲区保存**最近若干条**反思文本（滑动窗口，论文中通常 1~3 条）。
- 每条反思的形态大致是：`"I attempted X and got Y because Z. Next time I should do W."`
- 下一轮 prompt 的组装方式 = *原始任务描述* + *记忆缓冲区中的反思* + *（可选）上一次的完整推理轨迹*。

### 1.3 上游提供的现成消融开关

上游 `noahshinn/reflexion` 把"给不给上次信息"做成了枚举 `ReflexionStrategy`，可直接当我们的 A/B 对照组：

| 枚举 | 给模型什么 |
|---|---|
| `NONE` | 什么都不给（基线） |
| `LAST_ATTEMPT` | 只给上次的推理轨迹 |
| `REFLEXION` | 只给上次的自我反思 |
| `LAST_ATTEMPT_AND_REFLEXION` | 两者都给（完整版） |

### 1.4 评测任务与指标

| 任务域 | 环境 | 指标 |
|---|---|---|
| 推理 | HotPotQA（distractor 子集，100 题样本） | EM / F1 |
| 决策 | AlfWorld | 任务成功率 |
| 编程 | HumanEval / LeetCodeHardGym | **pass@1** |

### 1.5 方法步骤（可直接照做的七步法）

1. **定义任务集**：每个任务带一个可自动判定的成功条件。
2. **定义 evaluator**：给定轨迹输出标量 reward（可先用确定性规则，不必上 LLM judge）。
3. **跑第一次尝试**，完整记录轨迹（prompt、工具调用、工具返回、最终回答）。
4. **判分**：`reward < threshold` 即视为失败。
5. **生成反思**：把「任务 + 轨迹 + 失败原因」交给 LLM，要求输出一段可执行的改进说明。
6. **写记忆**：反思追加到缓冲区（滑动窗口）。
7. **重试**：把记忆作为上下文重新跑第 3 步，最多 `max_attempts` 次；成功即停。

### 1.6 在本项目的落点

Qwen-Agent 的 `Assistant.run()` 是**单轮**语义，所以闭环必须包在它外面：

```python
# 伪代码 —— 落点在 src/qwen_agent_demo/ 之上的新一层
reflections = []
for attempt in range(max_attempts):
    traj = run_assistant(task, memory=reflections)   # 复用现有 demo 的 Assistant
    reward, detail = evaluator(traj)                  # 第一版用确定性规则
    if reward >= threshold:
        break
    reflections.append(llm_reflect(task, traj, detail))   # 只在失败时产生
    reflections = reflections[-memory_window:]              # 滑动窗口
```

**必须注意的坑**：Qwen-Agent 自带的 `mem`（`self.mem.run()`）是**会话知识检索**（RAG 用的文档片段），**不是** Reflexion 的经验反思。两者语义完全不同，**反思记忆要放在框架之外**，否则会被当成知识片段检索，语义被冲淡。

**采集轨迹的位置**：`qwen_agent/agent.py` 的 `_call_tool()` 是工具调用的收敛点；消息序列里 `role == 'function'` 的条目就是完整工具轨迹（含入参与返回），这是后续所有轨迹级评测的输入来源。

## 2. OpenJudge —— 评测器工厂

### 2.1 原理

把「打分」这件事抽象成**可插拔的 grader**，每个 grader 具备：

- 一段**评测维度**的定义（如「是否选择了正确的工具」）
- 一段**输入映射**（把 agent 的 query / response / tool_calls 映射到 grader 的入参）
- 一份**基准数据集 + pytest 校验**，保证 grader 本身可信
- 输出：**分数 + 理由**（`result.score` / `result.reason`）

50+ 内置 grader 分为 General / **Agent** / Multimodal / Code / Skill / Finance 等类。其中 Agent 类直接对应我们的诉求：

| Grader | 评什么 |
|---|---|
| `Tool Selection` | 工具选择是否正确 |
| `Tool Parameter Check` | 工具参数是否正确 |
| `Plan` | 计划可行性 |
| `Memory` | 上下文/记忆保持 |
| `Trajectory` | 轨迹路径质量 |
| `Reflection` | 反思质量 |

### 2.2 三种评估策略

| 策略 | 语义 | 适用 |
|---|---|---|
| **Pointwise** | 绝对打分（这个回答得几分） | 常规回归评测 |
| **Listwise** | 排序（这几个里谁更好） | 模型/Prompt 比选 |
| **GRPO Tournament** | 对战式打分 | 无测试集时的相对排名（Auto Arena） |

### 2.3 Rubric 的三种生成方式

1. **自定义**：需求明确，直接写 Python 接口或 Prompt 模板。
2. **Zero-shot rubric 生成**：只给任务描述（可选样例），LLM 自动生成评测标准 → 适合原型期。
3. **数据驱动 rubric 生成**：用 `GraderGenerator` 从标注数据里总结 rubric → 适合已有业务数据的场景。

另有 **Agent-as-Judge**：把外部 CLI agent（Claude Code / Codex 等）当裁判，让它**真读代码、真跑代码**再打分，比纯 LLM 打分更可信。

### 2.4 方法步骤

1. **收集测试数据**：每条至少包含 `query` / `response`，涉及工具的再加 `context` / `tool_definitions` / `tool_calls`。
2. **选 grader + 配 mapper**：mapper 负责把我们的字段名对上 grader 的入参名。
3. **选 aggregator**：如 `WeightedSumAggregator(name='overall_score', weights={...})` 给出总分。
4. **批量跑**：`GradingRunner(grader_configs=..., aggregators=..., max_concurrency=5).arun(dataset)`。
5. **出报告**：`DistributionAnalyzer().analyze(dataset, results['overall_score'])`，看分布而不是只看均值。
6. **定位弱项 → 改 rubric 或改 agent → 重跑**，形成闭环。

### 2.5 在本项目的落点

- **我们已有的数据直接可用**：demo 跑完后，消息序列里天然含 `tool_calls`（工具名 + 参数）和最终 `response`，正好是 `ToolSelectionGrader` / `ToolParameterCheck` 的输入。
- **Judge 模型**：OpenJudge 的 `OpenAIChatModel` 支持自定义 base_url，**可以直接指向本机同一套 MiniMax 端点**；正式评测建议另配一个更强的裁判模型。
- **与 AgentScope 的关系**：官方提供 `OpenJudgeMetric` 适配器，把任意 `BaseGrader` 包装成 AgentScope 的 `Metric`，可直接嵌进 AgentScope 的 Benchmark 跑分。这是「用 AgentScope 跑评测」的标准路径。
- **规模化注意**：`max_concurrency` 建议先小后大，避免触发端点限流。

## 3. Claw-Eval —— 全轨迹可信评测

### 3.1 原理

Claw-Eval 的核心主张是：**只看 agent 的最终回答，无法判断它是不是"真的干完了"**。因此它做**全轨迹审计（full-trajectory auditing）**——审计整条执行轨迹，包括中间的工具调用、文件读写、网页操作。

### 3.2 规格

| 项 | 值 |
|---|---|
| 任务数 | **300 个人工校验任务** |
| Rubric 数 | **2,159 条** |
| 类别 | 9 类 |
| Split | `general` 161（通信/金融/运维/生产力等）、`multimodal` 101（网页生成、视频问答、文档抽取）、`multi_turn` 38（带模拟用户的澄清与建议） |
| 主指标 | **Pass^3** |
| 三维度 | **Completion**（是否完成）、**Safety**（是否避免有害/越权动作）、**Robustness**（多次试验是否稳定） |
| 裁判模型 | general + multimodal 用 `gemini-3-flash`；multi_turn 用 `claude opus 4.6`（同时充当 grader 与模拟 user-agent） |
| 集成 | 已支持 EvalScope 直接跑 |

**Pass^3 的含义**：任务要连续 **3 次独立试验（N=3）全部通过**才计一次成功。目的是消灭"侥幸通过"——单次跑对不代表 agent 真的具备该能力。网络/接口抖动导致的执行失败，官方做法是**手动重触发**，确保恰好生成 3 条有效轨迹。

### 3.3 方法步骤

1. **准备 fixture**：每个任务所需的初始文件/环境（`data/fixtures.tar.gz`）。
2. **跑 3 次**，保留 3 条完整轨迹。
3. **逐条 rubric 判定**：用裁判模型按 rubric 检查轨迹，而不是只看最后一句回答。
4. **三维度打分**：Completion / Safety / Robustness 分别判定。
5. **聚合 Pass^3**：3 次全过才算通过。
6. **失败模式归类**：把失败样本按原因归类，产出下一轮改进清单。

### 3.4 对我们最重要的两条结论

1. **安全不能只做拒答率统计。** Claw-Eval 的公开分析指出「44% 的安全违规被漏检」——因为违规发生在**中间的工具调用**里，而最终回答看起来完全正常。**必须做轨迹级审计。**
2. **单次跑通不算跑通。** Pass^3 的思想告诉我们：模型输出有随机性，回归基线应当跑 3 次取最差值（或全过才过），否则会掩盖退化。

## 4. 组合方案：本项目的四层评测/调优架构

把上面四个项目的思想按「成本从低到高、覆盖面从小到大」叠成四层：

| 层 | 名字 | 目的 | 手段 | 本次状态 |
|---|---|---|---|---|
| L1 | **协议层** | 保证底层可用 | 直接打 `/v1/chat/completions` 带 `tools`，断言返回 `tool_calls` | ✅ **已实现**（`model_factory.check_endpoint`） |
| L2 | **单元层** | 保证本地确定性逻辑正确 | 对本地工具做单元测试 | ✅ **已实现**（`tests/test_tools.py`） |
| L3 | **轨迹层** | 保证 agent 真的干完了、没越权 | Claw-Eval 式全轨迹 rubric 审计 + OpenJudge grader | ⬜ 待实现 |
| L4 | **反思层** | 失败后自动改进 | Reflexion 式反思记忆 + 重试 | ⬜ 待实现 |

### 接入点（基于上游源码确认）

```
L3 轨迹采集：qwen_agent/agent.py::_call_tool()  →  消息序列中 role='function' 的条目
L3 评判挂载：包住 Assistant.run()，拿到完整消息列表后交给 grader
L4 反思闭环：包在 Assistant.run() 外层，维护独立的 reflections 缓冲区（不要复用 Qwen-Agent 的 mem）
```

### 分阶段实施建议

- **阶段一（低成本）**：先用 OpenJudge 的 `Relevance` / `ToolSelection` / `ToolParameterCheck` 三个 grader，把 demo 的输出喂进去看基线分。
- **阶段二**：按业务方向自建 rubric（Zero-shot 生成起步），补 Completion 维度。
- **阶段三**：接 Reflexion 闭环，跑 L4 的"失败 → 反思 → 重试"，用 Pass^3 口径验证改进是否稳定。
- **阶段四**：把安全维度（见 `安全管控方法论.md`）并入同一套 grader，形成 Completion + Safety + Robustness 三维报告。
