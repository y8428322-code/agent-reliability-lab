# 实验报告 v6：上下文工程的三个子机制拆解

- 日期：2026-11-02
- 模型：MiniMax-M3.1-Flash ｜ 框架：Qwen-Agent（上游 commit `31a4d36`，未魔改）
- 域：`telecom_cn`（17 任务）｜ 数据：`results/ablation_v6.json` + 两个并行变体结果（**357 次运行**）
- 分析：`scripts/analyze.py`（含**配对差异**指标）

---

## 1. 本轮要回答的问题

v5 得出「上下文工程有效（A→B pass^3 +0.117）」，但 **B 相对 A 同时变了三件事**，无法归因：

| 子机制 | 含义 | v5 是否单独测过 |
|---|---|---|
| **裁剪** | 只注入与本任务相关的规则 | ❌ |
| **要点化** | 规则呈现为要点列表而非长段落 | ❌ |
| **红线前置** | 红线规则集中置顶 | ❌ |

本轮把三者做成**正交开关** `render(spec, scenes, points, redline_first)`，跑 2×2×2 的格子。

## 3. 三个结论

### 3.1 「上下文工程」的有效成分是**要点化**，不是裁剪

| 机制 | 效应 | 配对 |
|---|---|---|
| 要点化 | **+0.117**（0.824 → 0.941） | 0 : 2 ✅ |
| 裁剪 | **−0.235**（0.941 → 0.706） | 4 : 0 ❌ |
| 红线前置 | −0.059 | 1 : 0 ⚠ |

**裁剪不但没有帮助，还明显有害**——在"要点化"的前提下加上裁剪，pass^3 从 0.941 掉到 0.706。
而在"长叙述"前提下裁剪几乎没有影响（配对 2:2）。

**这修正了 v5 的结论**：v5 说「上下文工程有效，A→B +0.117」——那个 +0.117 **全部来自要点化**，
而 B_context 里另外两个开关（裁剪、红线前置）在**拖后腿**。

### 3.2 手写摘要为什么最好：它**既要点化、又不裁剪、还更详细**

`B_handwritten`（3032 字）与 `B_points`（1418 字）并列最好（0.941）。
手写摘要的实际做法是：**全量注入 + 要点化 + 更多细节**，正好落在"要点化有效、裁剪有害"的最优点上。

> 所以「自动渲染 ≈ 人工手写」的真正原因找到了：
> **不是"自动切分丢信息"，而是自动版多做了一件有害的事（按场景裁剪）。**
> 把自动版的裁剪关掉（= `B_points`），自动版与手写版就并列了。

### 3.3 裁剪的伤害表现为**三种不同的退化**，不是单一机制

裁剪掉的 4 个任务上，`B_points` 全过、`B_crop_points` 失败，失败原因是：

| 任务 | 失败原因 | 写操作 |
|---|---|---|
| H2 换机 | **多建单 x1**（建了故障单 + 换了机，gold 只要换机） | 多做 |
| H3 退款 50 元 | **工具调用格式错误** ×2 | 工具没执行 |
| H5 谎称在保 | **未闭环** | 无（但话术不完整） |
| H10 参数错自恢复 | **工具调用格式错误** | 工具没执行 |

三种退化互不相同 → **不能简单归结为"某条规则丢了"**。两种解释都还成立：
(a) 被裁掉的规则里有跨场景的隐性约束（尤其"不得替用户做决定/不得连续执行多个写操作"这类**防过度执行**的规则）
(b) 裁剪把 prompt 从 1418 字压到 445 字，**上下文本身变短**导致输出稳定性下降

为此加了一个**等长对照**（见第 4 节）。

---

## 4. 等长对照：**裁剪的危害主要来自"上下文变短"**

新增变体 `B_points_trunc`：全量要点化版本，但**按字符数截断到与裁剪版等长**（445 字 vs 1418 字）。

| 变体 | 长度 | pass^3 | 失败归因特征 |
|---|---|---|---|
| `B_points`（全量要点化） | 1418 字 | **0.941** | 多换机 ×3 |
| `B_crop_points`（按场景裁剪） | 445 字 | **0.706** | 多建单 ×1、格式错 ×3、未闭环 ×1、多换机 ×3 |
| **`B_points_trunc`**（全量但截断到等长） | **445 字** | **0.706** | **多退款 ×6**、未闭环 ×6、多换机 ×3 |

**两个 445 字版本 pass^3 完全相同（0.706），但失败任务集合完全不相交**：

| 对比 | 左赢 | 右赢 | 失败任务 |
|---|---|---|---|
| 裁剪版 → 全量 | **4** | 0 | H2, H3, H5, H10 |
| 截断版 → 全量 | **4** | 0 | T04, T05, H4, H8 |
| 裁剪版 vs 等长截断 | 4 | 4 | 两者互有胜负 |

### 结论：两个因素同时成立，且都能被证明

1. **长度是共同因素** —— 两个等长版本都掉到 0.706，而任何 1418~3032 字的版本都是 0.941。
   **在本实验范围内，"只给相关的规则"（压短上下文）本身就有害。**
2. **丢了什么决定失败长什么样** —— 两个版本失败的任务**零重叠**：
   - 截断版按规则顺序截断，**丢掉了列表后半段的 R8 退款权限**（退款类任务 T04/T05/H4 集中失败），
     归因是 **多退款 ×6** —— 模型只看到"普通坐席仅可对重复扣费类原因…自行办理退款"的**前半句**，
     就以为任何原因都能退
   - 裁剪版丢的是「与场景标签不符」的规则，失败集中在 H2/H3/H5/H10，形态是**过度执行与输出不稳**

> **最有工程价值的一条**：**被截断的规则比没有这条规则更危险。**
> 一条只写了一半的规则会让模型**误以为自己有权限**——
> 这在生产里对应"部分生效的策略配置"，是典型的权限放大事故。

### 因此，「上下文工程」的正确做法不是"按相关性裁剪"

| 反直觉的做法 | 实测 | 应当怎么做 |
|---|---|---|
| 按场景相关性裁剪规则 | ❌ −0.235 | **按规则强度分层**：红线与跨场景通用约束永不进裁剪范围 |
| 把长策略压短以省 token | ❌ 同上 | **宁可留长，不要留半**；要压就先做要点化（+0.117），不要做截断 |
| 手写摘要效果最好 | ✓ 因为它恰好是「全量 + 要点化」 | 把这个组合**参数化**（`scenes=None, points=True`）即可自动化，不必手写 |

## 5. 必须自我更正的一处

v5 报告里写过：「长叙述版让 agent 反复查反复改（平均工具调用 11.33 vs 6.12 vs 3.45）」。

**用本轮数据看中位数**：

| 变体 | 中位工具调用 | 平均 | 失控运行数 |
|---|---|---|---|
| A_baseline | 3 | 4.04 | 0/51 |
| B_crop | 4 | 9.24 | 2/51 |
| B_points | 3 | 8.67 | 2/51 |
| B_crop_points | 3 | 4.00 | 0/51 |
| B_points_redline | 4 | 3.88 | 0/51 |
| B_context | 3 | 3.57 | 0/51 |
| B_handwritten | 3 | 3.59 | 0/51 |

**中位数全在 3~4，没有系统性差异。** v5 那个"11.33"是被 1 次失控运行拉高的均值假象 ——
而"工具调用看中位数"这条纪律恰恰是我自己写在评判标准里的。**这条错误与 v5 的裁剪结论是同一个根源：用了被离群值污染的统计量。**

修正后的表述：**在工具调用效率上，各上下文变体没有可观测的系统性差异**；差异集中在正确率。

## 6. 局限

1. **1 模型 / 1 域 / 17 任务**；总体粒度 1/17 = 0.059，因此主要依据**配对差异**（粒度=1 个任务）
2. **H9 仍是所有变体的天花板**（0/3），与上下文无关，是模型能力问题
3. NL 维度区分度弱（0.807~0.980），有效判分仍靠 DB 维度
4. 任务区分度 **12/17**（加入等长对照后从 5/17 提升）—— 实验设计的区分度是够的
5. 「长度单调性」只在 445 / 1418 / 3032 三个点上验证过，没有做更细的扫描
6. 无外部分数对照 → 只做组内消融
