- 日期：2026-11-02
- 模型：MiniMax-M3.1-Flash ｜ 框架：Qwen-Agent（上游 commit `31a4d36`，未魔改）

- 判分标准（跑前写死）：见 `docs/审计与评判标准.md` 第 6 节

## 1. 本轮做了什么

v6 的结论是「**按场景裁剪有害**（0.941 → 0.706）」。但回审发现 v6 把两个变量**混在了一起**：

> `redline_first=False` 时，红线规则被留在各自分节里 → **按场景裁剪时红线一起被裁掉**。
> 例如「欠费不建单」（红线，category=repair）在换机任务上直接消失。

所以 v6 测的其实是「**裁剪 + 丢红线**」，不是「裁剪」。

本轮把「**是否保留**」与「**是否置顶**」彻底解耦，做三档裁剪策略：

| 变体 | 红线 | 跨场景通用约束 | 场景规则 |
|---|---|---|---|
| `B_points` | 全量 | 全量 | 全量（**不裁剪**） |
| `B_crop_points`（旧） | **裁掉** | **裁掉** | 按场景 |
| **`B_crop_keepredline`** | **保留** | 裁掉 | 按场景 |
| `B_crop_safe` | 保留 | 保留 | 按场景 |

## 2. 结果（204 次运行，0 中断）

| 变体 | 裁剪策略 | pass@1 | **pass^3** | DB | NL | 失败归因 |
|---|---|---|---|---|---|---|
| `B_points` | 不裁剪（全量） | 0.824 | 0.765 | 0.922 | 0.928 | 未闭环 ×5、多换机 ×2、多建单 ×1、格式错 ×1 |
| `B_crop_points` | 严格按场景裁（红线也裁） | 0.863 | 0.765 | 0.922 | 0.954 | 未闭环 ×3、多换机 ×3、多建单 ×1 |
| **`B_crop_keepredline`** | **裁剪但保留红线** | **0.941** | **0.941** | **0.941** | 0.967 | 多换机 ×2、少建单 ×1 |
| `B_crop_safe` | 裁剪 + 红线 + 通用约束 | 0.882 | 0.824 | 0.941 | 0.954 | 未闭环 ×3、多换机 ×3 |

|---|---|---|---|
| B_crop_points → B_crop_keepredline | 0 | **3** | **+3** |

| B_points → B_crop_safe | 1 | 3 | −2 |

## 3. 三个结论

### 3.1 **v6 的结论是错的**——那是一次变量耦合造成的假象

| | v6（红线与裁剪混在一起） | v7（解耦后） |
|---|---|---|
| 全量注入 | 0.941 | **0.765** |
| 裁剪 | 0.706 | **0.941**（保留红线时） |
| 结论 | 「裁剪有害」 | **「裁剪有益，前提是保留红线」** |

**裁剪策略本身是好东西；v6 之所以显示它有害，是因为它顺手把红线也裁掉了。**
这正是"保留 vs 置顶解耦"的价值 —— 如果不拆开，就会把一个**实现缺陷**误判成**方法论结论**。

### 3.2 「上下文工程」的正确配方：**裁剪到场景相关 + 红线保底 + 要点化**

`B_crop_keepredline`（0.941）**同时优于**全量注入（0.765）和旧裁剪（0.765）。

为什么全量注入反而更差？因为全量把**不相关场景的规则**也塞进去了
（比如换机任务里塞着退款权限、撤单条件、故障类型取值）——噪声干扰判断。
而「裁剪 + 红线保底」既精简又保底：

> **给最少够用的上下文，但把"绝对不能违反"的规则无条件保留。**

### 3.3 但**不要**把"过程性约束"设为跨场景通用——会矫枉过正

`B_crop_safe`（在 keepredline 基础上再加 R15/R17 通用约束）**反而降到 0.824**，配对 **2:0 输给** keepredline。

机制（读轨迹确认）：

```
H7 欠费账户要求换机
  B_crop_keepredline  t1/t2/t3  tools=3  → 3/3 通过（查了状态再答）
  B_crop_safe          t1        tools=0  → 文本说"未告知"细节
                       t2/t3     tools=0  → 未闭环
```

新增的两条通用约束：
- **R15**「不得替用户做决定」「不得在未告知用户时连续执行多个写操作」
- **R17**「同一错误连续两次仍失败就停止重试」

被 agent 理解成了 **"别多做事、别多查询"** → **连必要的查询都不做了**（tools=0）→
回答缺少基于查询结果的具体信息 → NL 断言不过。

> **这是从 v6 到 v7 的一处矫枉过正**：v6 的失败是"做多了"，我加禁止性规则去压它，
> 结果把行为推向另一个极端 —— **从"过度执行"翻转成"该做不做"**。
> **用禁止性规则压制越界行为，会让模型变得畏首畏尾**；要修"做多了"，
> 正确的方向是**收紧可行域**（机制约束），不是**增加禁令**（文字约束）。

### 3.4 预注册判分标准的检验结果

| 标准 | 结果 |
|---|---|
| ① `B_crop_safe` ≥ `B_points`（安全裁剪无损失） | ❌ **不成立**（0.824 < 0.765 是成立，但 < 0.941 不成立）→ 实际是 keepredline 达标 |
| ② `B_crop_safe` ≥ `B_crop_keepredline` ≥ `B_crop_points` | ❌ **不成立**（safe < keepredline） |
| ③ 「多做」类失败在安全裁剪上归零 | ❌ 未归零（多换机 ×3 仍在） |
| ④ 唯一达标的是 `B_crop_keepredline` ≥ `B_crop_points` | ✅ **0.941 vs 0.765，配对 3:0** |

**结论必须改写**（这是预注册的价值：逼我承认"安全裁剪"的完整方案反而更差）：
最好的策略是 **裁剪 + 只保红线**，而不是裁剪 + 保红线 + 保通用约束。

## 4. 本轮自身也踩了一个坑：并行限流污染实验

首跑（4 并发）所有变体分数从 ~0.9 掉到 ~0.55，失败模式整体从"多做"翻转成"少做"。

排查：**23/204 次运行以 `Maximum number of retries (2) exceeded` 中断**
（上游用 `openai.OpenAI()`，SDK 默认 `max_retries=2`，限流即抛错），
而**中断的运行被当成"任务失败"计进正确率**。

修复三处：① `CompatOAI` 给所有 API 调用套指数退避重试；
② 中断的运行标记 `aborted`，与"模型答错"分开统计；
③ 默认并发降到 2。重跑后 **0 次中断**，结论才可信。

> **教训**：**基础设施故障必须与模型能力失败分开统计**。
> 这与之前"均值被离群值污染""阈值未考虑分辨率"是同一族错误的三个变体 ——
> **都是"统计口径没把非模型因素隔离出来"**。

## 5. 局限

1. **1 模型 / 1 域 / 17 任务**；总体粒度 1/17 = 0.059，主要依据配对差异
2. **本轮规则集与 v6 不同**（新增 R16/R17、R15 标 universal），v6 与 v7 的绝对分数**不可直接比**；
   v6 的结论作为历史测量保留，解耦后的结论以 v7 为准
3. **H9 仍是所有变体的天花板**（0/3），与上下文无关
4. NL 维度区分度弱（0.928~0.967），有效判分靠 DB 维度
5. 任务区分度降到 4/17（本轮变体之间的差异变小，因为最好的变体接近满分）
6. 无外部分数对照 → 只做组内消融
