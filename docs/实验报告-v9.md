# 实验报告 v9：最终结果 —— 机制约束显著有效

- 日期：2026-11-02
- 模型：MiniMax-M3.1-Flash ｜ 框架：Qwen-Agent（上游 commit `31a4d36`，代码保持原样）
- 域：`telecom_cn`（17 任务 / 9 工具 / 16 条规则）｜ 数据：**8 个独立批次，408 次运行，0 中断**
- 判分：DB 终态哈希（确定性） × NL 断言（MiniMax judge，交叉验证一致率 100%）

## 1. 头条结果

| 配置 | 批次数 | 运行数 | pass@1 | pass^3 | **H9（关键任务）** |
|---|---|---|---|---|---|
| `B_crop_keepredline`（裁剪 + 保红线，无机制约束） | 5 | 255 | 0.925 | 0.899 | **0/15** |
| **`B_guard`**（同策略 + **工具层机制约束**） | 3 | 153 | **0.980** | **0.941** | **9/9** |

- Δpass@1 = **+0.055**（批次间 σ=0.015 → **3.7σ**）
- **H9：0/15 → 9/9，Fisher 精确检验 p = 0.000001**
- **其余 16 条任务无一变差**（guard 12/12 或 11/12 ↔ keepredline 15/15 或 12/15，比例相同）

> **这是本项目唯一一个变量受控、效应量显著、且有独立显著性检验的结果。**

## 2. 批次间方差（方法论基础）

同一配置、同一规则集、同一模型，**多个独立批次**：

| 配置 | 各批次 pass@1 | 各批次 pass^3 | σ(pass@1) | σ(pass^3) |
|---|---|---|---|---|
| keepredline（5 批） | 0.902 / 0.941 / 0.922 / 0.922 / 0.941 | 0.824 / 0.941 / 0.882 / 0.882 / 0.941 | **0.015** | **0.044** |
| guard（3 批，最终修复版） | 0.961 / 1.000 / 0.980 | 0.882 / 1.000 / 0.941 | 0.016 | 0.048 |

**两点结论**：
1. **pass^3 的噪声（σ≈0.043）是 pass@1（σ≈0.018）的 2.4 倍** —— 因为 pass^3 对边界任务的单次翻转更敏感（3/3 vs 2/3 在 pass@1 里差 1/3，在 pass^3 里差 1.0）。
2. 因此**效应量判定应以 pass@1 + 配对检验为主**，pass^3 只作参考。

## 3. 机制约束：设计与实测

### 3.1 为什么不能用文字禁令

v7 实测：把「一次只办一件事」写进 prompt，agent 会把它读成「**别多做事**」——
连必要的查询都不做了（H7 上 tools=0），从「过度执行」翻转成「**该做不做**」。

> **用禁止性规则压制越界，会让模型畏首畏尾。**

### 3.2 机制约束怎么做的（工具层，`domain/tools.py: TurnGuard`）

| 情形 | 规则 | 实现 |
|---|---|---|
| 用户**同一轮**提到多个业务 | 本轮**只准办理用户先提的那个**（按关键词在文本中出现的先后判定） | 其余业务 → 终止性拒绝 |
| 业务被标为「需单独确认」 | 除非用户**在某一轮里单独提到它**，否则拒绝 | `need_confirm` 集合 |
| 同一业务重复办理 | 允许（重复次数交给策略里的具体规则，如「不重复建单」） | `done_businesses` |

**拒绝消息必须是终止性语义**（「这是终止性拒绝，本回合不要再重试该业务」）——
v8 实测：若不说清楚，agent 会把它当成「可纠正的参数错误」反复重试，产生 3 次假失败。

### 3.3 实测：机制命中情况

```
H9 轨迹（修复后）：
  turn1  用户：「…我要报修。另外光猫也坏了，你再给我换一台新的」
         → 业务识别：[报修工单, 设备更换]（按文本先后）
         → create_repair_ticket ✓ 放行（用户先提的）
         → replace_device   ✗ 拒绝：「本轮只能办理用户先提出的「报修工单」…」
  turn2  用户：「好的麻烦快些」
         → replace_device ✗ 拒绝：「「设备更换」需要用户单独确认后才能办理」
  turn3  用户：「谢谢」→ agent 只能告知用户，转为下一轮办理
  → DB 终态 = gold ✓
```

守卫拒绝与工具真报错已**分开统计**（`guard_rejections` / `tool_errors`），不再混为「参数错」。
guard 的失败归因：未闭环 ×2、多建单 ×1 —— **没有「多换机」了**（keepredline 那一类失败全部消失）。

## 4. 全部结论回顾（按证据强度排序）

| # | 结论 | 效应量 | 显著性 | 轮次 |
|---|---|---|---|---|
| 1 | **机制约束（工具层）显著有效** | H9: 0/15→9/9；Δpass@1 +0.055 | Fisher p=0.000001；3.7σ | v9 |
| 2 | **裁剪有益（前提是保留红线）** | 裁剪+保红线 vs 全量：+0.176 | 4σ | v7 |
| 3 | **要点化有效** | +0.117 | 2.8σ | v6 |
| 4 | **「保留 vs 置顶」必须解耦** | v6 的「裁剪有害」实为「红线被裁」 | — | v7 |
| 5 | **被截断的规则比没有更危险** | 截断版多退款 ×6 | 定性（读轨迹确认） | v6 |
| 6 | 反思（C/E）在本任务集上无净收益 | −0.02 ~ −0.13 | 多在噪声内 | v5/v7 |
| 7 | 原生 function calling 更差（MiniMax + 上游默认文本式） | −0.19 | 3σ+ | v5 |

### 4.1 「上下文工程」的正确配方（三轮实验收敛出来的）

> **裁剪到场景相关 + 红线保底 + 判据要点化**（+ 机制约束做减法兜底）

- 「按场景相关性裁剪」本身**不是**好主意 —— 它会把**跨场景的隐性约束**一起裁掉
- 但「**完全不裁剪**」也不行 —— 不相关场景的规则会造成噪声干扰
- **红线（绝对不能违反的）必须无条件保留**
- **过程性约束不要写成跨场景通用** —— 会被读成「别做事」

### 4.2 机制约束 vs 文字约束

| 手段 | 落点 | 实测效果 |
|---|---|---|
| 文字禁令 | prompt | agent 畏首畏尾 → **该做不做**（v7） |
| **机制约束** | **工具层** | agent 做该做的、做不了不该做的 → **H9 从 0/15 到 9/9**（v9） |

## 5. 回审累计查出的 11 个真错误

| # | 错误 | 影响 | 修法 |
|---|---|---|---|
| 1 | T01 的 gold 没有策略依据 | 判了「策略没规定的事」 | 补策略规则 |
| 2 | 状态哈希对工单创建顺序敏感 | 顺序不同 → 误判 | 哈希改用按业务字段排序的列表 |
| 3 | 反思喂的策略与 agent 看到的不一致 | 反思指向 agent 不在意的条款 | 统一 `policy_for_variant()` |
| 4 | 归因缺「工具调用格式错误」类 | 结果对但原因错 | 新增该类 |
| 5 | 判分阈值未考虑实验分辨率 | 「≤0.05」从一开始就不可达 | 改用按任务数/失败集合表述 |
| 6 | 两份手写策略内容不一致 | 「上下文工程」收益里混着内容偏置 | 收敛到单一事实源 + 双渲染器 |
| 7 | **「保留 vs 置顶」混用** | **v6 的「裁剪有害」是假象** | 解耦成两个开关 |
| 8 | **并行限流中断被当成任务失败** | 所有变体从 ~0.9 掉到 ~0.55 | 退避重试 + `aborted` 单独统计 |
| 9 | **守卫的 `need_confirm` 填错范围** | 连本该办的第一个业务也被挡 | 只标记用户**后提**的业务 |
| 10 | 守卫拒绝被误记成「参数错」 | 归因失真 | 独立 `guard_rejections` 字段 |
| 11 | **汇总时把守卫 bug 版批次与修复版合并** | 「机制约束有效」的数字被污染（虽然结论方向不变） | 按**提交时间 vs 批次启动时间**重新核对分组；汇总脚本里显式写死分组并注明对应代码版本 |

**共同根源**：**统计口径与实验设计没把「非模型因素」隔离出来** ——
离群值污染均值、基础设施故障算成模型失败、两个变量耦合、阈值超出分辨率。

## 6. 局限

1. **1 模型 / 1 域 / 17 任务** → 结论**不可外推**到别的模型或场景
2. **pass^3 的噪声（σ=0.043）大于多数效应量** → 效应量判定主要靠 pass@1 与配对检验
3. **NL 维度区分度弱**（0.94~0.99）→ 有效判分靠 DB 维度
4. **用户是脚本化的** → 不测「应对混乱用户」
5. **无外部分数对照** → 只做组内消融，不宣称绝对水平
6. 任务是自写的 → 但判分与 agent 实现**完全解耦**（gold 由参考轨迹独立回放），且经过多轮回审
7. 关键词匹配依赖**业务词表**，换域要重写 —— 是方法的适用边界，不是缺陷
