# 回审记录与评判标准

> 本文档记录**每一步之前的全量回审**结果，以及「当前结果凭什么算好」的**评判标准**。
> 审计方法：人工逐条核对 v4 的全部失败运行 → 找出判分/归因的偏差 → 修 → 重跑。

## 1. v4 结果的人工核查（20 次失败逐条对照策略）

### 1.1 结论：20/20 **判错都判对了**

| 归因 | 次数 | 人工核查结论 |
|---|---|---|
| 状态不符(多建单 x1) | 8 | ✓ 全部正确 |
| 状态不符(多换机 x1) | 8 | ✓ 全部正确 |
| 状态不符(少建单 x1) | 2 | ✓ 全部正确 |
| 未闭环 | 2 | ✓ 正确（agent 确实没给出实质答复） |

**判分准确率 = 20/20 = 100%**（样本为 v4 的全部失败运行；v4 的成功运行由 DB 哈希精确判定，不存在"蒙对"）

### 1.2 但归因有 2 条不准 → 发现一个**新的失败模式**

`A_baseline H9 trial=3` 与 `E_guarded_reflect H9 trial=3` 的 agent 最终回复是：

```
客服: tool_call>
{"name": "replace_device", "arguments": {"customer_id": "C1008", ...}}
</tool_call>          ← 闭合标签内含零宽字符 U+200B
```

即：**模型确实想调用工具，但 `<tool_call>` 标签格式损坏（未闭合 / 含零宽字符），
上游 Nous 文本解析失败 → 工具根本没执行 → 残缺文本被原样吐给用户。**

DB 维度看到的是"少做了一件事"，判**结果**是对的；但归因标签写成「未闭环」是不准确的，
真实原因是**「工具调用格式错误」**——这是一个**新的失败类型**，当前归因体系没有覆盖。

**为什么必须单独记一类**：DB 判分只能看到"状态没变"，**无法区分**
「agent 压根没尝试」和「agent 尝试了但格式坏了」——两者的改进手段完全不同
（前者是决策问题，后者是**协议/解析问题**）。

**修法（P4-1，已完成）**：
- 归因时检查 assistant 文本里是否残留写坏的 `tool_call` 片段，且**对应工具确实没被执行**
  （若工具已执行、只是文本里留着一段，属于无害冗余，不记为失败）
- 格式错误改为**独立于成败的质量指标** `result.format_error`，
  失败时它就是失败原因，成功时也照记（用于统计上游缺陷发生率）

**修正后的效果（用 v4 数据重新归因，无需重跑模型）**：

| 变体 | 任务 | trial | 原归因 | 新归因 |
|---|---|---|---|---|
| A_baseline | H9 | 3 | 未闭环 | **工具调用格式错误** |
| D_guarded | H9 | 2 | 状态不符(少建单 x1) | **工具调用格式错误** |
| D_guarded | H10 | 3 | 状态不符(少建单 x1) | **工具调用格式错误** |
| E_guarded_reflect | H9 | 3 | 未闭环 | **工具调用格式错误** |

**归因准确率 90% → 100%（20/20）**；新指标「格式错误发生率」= **4/255 = 1.6%**。

> 附带发现：上游 Qwen-Agent 的文本式 function calling **不校验**模型输出的
> `<tool_call>` 标签是否合法，坏了就直接把原文吐给用户。
> 这在生产里意味着**用户会看到一堆 JSON 片段**——真实的产品级缺陷。

### 1.3 顺带修正一处口径

`A_baseline T03 trial=2` 归因为「多建单 x1」——gold 是"完全不写库"，agent 建了 1 张故障单，
相对 gold 确实是"多了 1 张单"，语义正确 ✓（T03 用户只要求换机、没要求报修）。

### 2.1 第 9 项说明

17 条任务里，**12 条所有变体都是 3/3**（完全无区分度），只有 5 条（T01/T03/H2/H9/H10）能区分变体。
**任务区分度本身必须被当作一个指标来管**，否则"pass@1 提升"可能只是样本噪声。

按当前失败归因反推，**缺的是这几类任务**：
- **规则检索类**（规则埋在长文本里，测能不能检索到并应用）——只有 T01 一条，应扩充
- **边界类**（恰好在阈值上/下）——已有 H3/H4，应扩到更多维度
- **跨条款交互类**（两条规则同时触发，需判断优先级）——**完全没有**，应补
- **信息不全需澄清类**——只有 H6/H10 两条

### 2.2 还缺一类"答案对照"

目前所有对照都来自**我们自己写的 gold**。缺的是**独立第二意见**：
用 LLM 评审（读 policy + 读轨迹，独立判断行为是否合规）与 DB 判分交叉，算**一致率**。
这是判断"DB 判分本身可信不可信"的必要手段（DB 判分只看终态，不看过程是否合规）。

## 3. 下一阶段（P4）做什么，以及"评判标准"是什么

| 动作 | 评判标准（判定它有没有意义） | 状态 |
|---|---|---|
| **P4-1 归因补「工具调用格式错误」类** | 归因准确率从 90% → 100%；新类能被自动检出 | ✅ 已完成（用 v4 数据重算，20/20） |
| **P4-2 策略单一事实源 + 自动切分** | **自动生成的摘要 vs 人工写的摘要**，在同一任务集上 pass^3 相当（差距 ≤0.05）。若相当 → 「上下文工程」是可迁移的**方法**而非手艺；若人工版明显更好 → 说明人工摘要携带了额外知识，结论要改写 | 🔄 进行中（255 次运行） |
| **P4-3 补任务提高区分度** | 区分度 5/17 → ≥8/17 | ⬜ |
| **P4-4 约束下沉到工具层** | H9 类"过度执行"任务的失败率下降，且**不产生新的过度保守失败**（少做类归因计数不上升） | ⬜ |
| **P4-5 独立 LLM 评审交叉验证** | 与 DB 判分的一致率 ≥90% | ⬜ |

**P4-2 是本阶段的核心**，因为它回答的是本项目最初的问题：
「上下文工程到底是一门手艺，还是一套可复用的方法？」

### 3.1 P4-2 的实现要点

#### ⚠ 判分标准本身的修正（跑完后发现）

我事先定的标准是「自动版与手写版 pass^3 差距 ≤0.05」。**这个标准从一开始就不可达**：

> 17 个任务、每个任务权重 1/17 = **0.0588**。
> 任何**单个任务**的翻转就会让 pass^3 变化 0.059 —— 这是本实验能分辨的**最小差异**。
> 因此任何小于 0.059 的比例阈值都**没有统计意义**。

**修正后的标准**（用任务数与失败集合表述，而不是比例）：

| 标准 | 判定 |
|---|---|
| 自动版与手写版的**失败任务集合**是否一致 | 差 ≤1 个任务，且该任务需人工判读原因 |
| 差异任务的原因 | 是**规则覆盖差异**（说明自动切分丢信息）还是**行为随机性**（说明是噪声） |
| 工具调用效率 | 自动版应不多于手写版（手写版更长，成本更高） |

> **教训**：判分标准本身也要被审查。定阈值时没考虑**实验的分辨率**（任务粒度），
> 就会得到一个永远达不成、或者被单个样本决定的标准。

### 3.2 实现要点

**问题**：此前 `policy.md`（手写长文）与 `policy_digest.md`（手写结构化摘要）两份**内容并不严格一致**，
于是「上下文工程」的收益里混进了「人工摘要多写了 / 漏写了什么」的偏置，
**无法干净地归因给"呈现方式"这个变量**。

**做法**：

```
domain/policy_rules.yaml   ← 唯一事实源（16 条规则）
        │  每条含：id / 标题 / 分组 / 是否红线 / 适用场景 / 叙述正文 body / 关键判据 criteria
        ├── render_narrative()    → 长叙述版：按分节拼正文，规则标题不出现、判据不单列
        └── render_structured()   → 结构化版：红线前置 + 分节 + 判据要点化 + 按任务场景裁剪
```

变体与策略来源：

| 变体 | 策略来源 | 长度（identity+repair+multi+speech 场景） |
|---|---|---|
| `A_baseline` | 自动渲染的长叙述版 | 1677 字 |
| `B_context` | 自动渲染的结构化版 | 1319 字 |
| **`B_handwritten`** | **人工手写**摘要 | 3032 字 |
| `D_guarded` / `E_guarded_reflect` | 同 B + 各自机制 | 1319 字 + 约束/反思 |

**这轮跑完后能回答什么**：
1. **A → B 的差距**（同源、只差呈现方式）= 「上下文工程」本身的效应，可干净归因
2. **B_auto → B_handwritten 的差距** = 自动切分能否替代人工撰写
   - 差距 ≤0.05 → 自动版可替代手写，**上下文工程是可迁移的方法**
   - 人工版明显更好 → 人工摘要携带了额外知识，结论要改写（不是"方法"而是"手艺"）
3. 注意手写版反而**更长**（3032 vs 1319 字）—— 若性能相当，自动版在 token 成本上还占优

**为什么必须重跑**：A/B 的策略来源变了（原手写 policy.md vs 现在自动渲染的长叙述版），
旧的 v4 数字不再可比。

## 4. 回审清单（每一步开工前逐条过）

1. 判分逻辑：gold 回放是否平凡通过？故意错误是否必然失败？
2. gold：每条是否都能由策略推出？策略与 gold 是否双向一致？
3. 变体：是否每级只差一个变量？有没有跨变体的隐式差异（prompt 长度、全局状态、随机性）？
4. 指标：pass^k 公式、聚合方式、是否被离群值污染（工具调用看中位数）？
5. 失败归因：标签是否覆盖全部失败类型？有没有"结果对但原因错"？
6. **判分器本身**：有没有独立第二意见？人工核查覆盖率多少？
7. 意义性：这个实验能支撑什么结论、不能支撑什么？结论有没有被过度解读？
8. 遗漏细节：有没有失败类型是"看起来对其实错"的？有没有 silent failure？

## 5. P0「安全裁剪」实验：判分标准（跑前写死）

**目标**：验证"按规则强度分层裁剪"能否消除 v6 发现的裁剪危害。

**改造前后的三档策略**（同一份规则集，只差裁剪策略）：

| 变体 | 红线 | 跨场景通用约束 | 场景规则 |
|---|---|---|---|
| `B_crop_points`（旧） | **裁掉** | **裁掉** | 按场景 |
| `B_crop_keepredline`（中） | 保留 | 裁掉 | 按场景 |
| `B_crop_safe`（新） | 保留 | 保留 | 按场景 |
| `B_points`（基准） | 全量 | 全量 | 全量 |

**判分标准**（先定死，防止事后找理由）：

1. `B_crop_safe` 的 pass^3 **≥** `B_points` —— 安全裁剪**不应有正确率损失**
2. `B_crop_safe` **≥** `B_crop_keepredline` **≥** `B_crop_points` —— 分层策略逐级改善
3. 若 1 不成立（安全裁剪仍有损失），则说明**"裁剪"这个动作本身就有害**，
   结论要改写成"不要裁剪，全量注入 + 要点化"
4. 「多做」类失败归因（多建单 / 多换机 / 多退款）在 `B_crop_safe` 上应**归零**

**注**：本轮规则集有变化（新增 R16/R17、R15 标 universal），故与 v6 的数字**不可直接比**，
只在本轮内部可比。v6 的结论（裁剪有害）作为**历史测量**保留。

## 7. P0「规则强度分层」实验的预注册判分标准（跑前写死）

**改动内容**（规则集，legacy → current）：
- R15「不得替用户做决定」→「以用户明确诉求为依据」，**提为红线**（原为 multi 分组的非红线）
- R5「保修以系统为准」补充「判定为过保后要告知具体日期并给替代方案」
- R11「闭环告知」补充「工单当前状态」
- **新增 R18「不得声称未完成的操作已完成」**（红线）

**动机来自数据**：1224 次历史运行里，「未闭环」是最大失败类（50 次），抽检发现其中一部分是
agent **谎称已办理并未发生的事**（断言「没有声称已办理退款/换机」失败）；同时 R15 因为归在
multi 分组，**在 17 个任务里有 16 个根本看不到它**。

**对照设计**（两个正交变量，各自只差一个）：

| 对比 | 只差的变量 |
|---|---|
| `B_guard` vs `B_guard_redline` | 规则集（守卫相同） |
| `B_crop_keepredline` vs `B_crop_redline` | 规则集（都无守卫） |

**判分标准**：

1. `B_guard_redline` 的 pass@1 与 pass^3 **都不低于** `B_guard` → 规则集改动有净收益
2. `B_crop_redline` **不低于** `B_crop_keepredline` → 同上，在没有守卫时也成立
3. **不出现新的「该做不做」**：单轮工具调用数为 0 的运行数不上升
   → 说明 R15 提为红线没有重演 v7 的「畏首畏尾」
4. 「谎称已办理」类失败计数下降 → R18 有效
5. 若 1 或 2 不成立 → 结论是**规则集改动无效**，并区分原因：
   R15 措辞问题（畏首畏尾）还是 R18 本身没用

**若 3 不成立**：把 R15 保留为非红线，但**改写措辞**（强调"以用户明确诉求为依据"而非"不要连续做"），
再跑一轮——这样能把"R15 的位置"与"R15 的措辞"两个因素分开。

---


同一配置（`B_crop_keepredline`）、同一规则集、同一模型，**两个独立批次**：

| 批次 | n | pass@1 | pass^3 |
|---|---|---|---|
| A（v8） | 51 | 0.902 | 0.824 |
| B（v9） | 51 | 0.941 | **0.941** |
| **批次间差** | | 0.039 | **0.125** |

逐任务看：只有 **2/17** 个任务不一致（H5、H10，都是 2/3 vs 3/3 的边界抖动），
其余 15 条两批都是 3/3 —— 说明噪声**高度集中在少数边界任务**，
但因为 pass^3 是逐任务等权平均，少数任务翻转就能把总分推动 0.06~0.12。

### 6.5.1 这意味着什么

| 结论 | 幅度 | 是否超出噪声 0.125 |
|---|---|---|
| v6「裁剪有害」 | −0.235 | ✅ 超出（1.9×） |
| v7「裁剪有益」 | +0.176 | ⚠ 勉强（1.4×） |
| v8「机制约束有效」 | +0.117 | ❌ **不超出（0.9×）** |

→ **v8 的结论不可靠**（虽然它的配对差异 2:0 方向一致，但样本只有 2 个任务）。
→ v6/v7 的结论需要用**多批次合并**重估。

### 6.5.2 由此定下的实验规范（写死，后续都按这个来）

1. **每个配置至少 3 个独立批次**（每批 17 任务 × 3 trial），合并后按任务算 pass^3。
2. **报告必须同时给出批次间方差**，否则读者无法判断差异是否真实。
3. **优先报配对差异**（同一任务上逐对比，粒度=1 个任务），它比总体 pass^3 灵敏。
4. **结论的门槛**：效应量必须 **> 合并后的批次间标准差**，否则只报"未观察到显著差异"。

> **这才是本项目最贵的一课**：前面 v6/v7/v8 的很多"结论"，其实是在噪声里读信号。
> 判分标准、gold、断言、变量耦合、基础设施故障、**实验分辨率**——
> 六类问题里，最后这一类最难发现，也最致命。
| P0 首跑 | 结果与 v6 差距过大（所有变体从 ~0.9 掉到 ~0.55），先怀疑规则集，再查运行级异常 | ❌ **不是规则集的问题**：23/204 次运行被端点限流中断（`Maximum number of retries (2) exceeded`），而**中断被当成"任务失败"计进正确率** → 是我的实验设计错误（4 并发过高） |

### 7.1 P0 首跑踩的坑：基础设施故障混进了正确率

**现象**：4 变体并发跑完，所有变体分数从 v6 的 ~0.9 掉到 0.53~0.65，且失败模式从"多做"整体翻转成"少做"。

**排查过程**：
1. 先怀疑规则集改动（R16/R17 新增、R15 变 universal）→ 查"少做"类失败是否伴随工具报错 → **0% 伴随**，排除 R17「遇错停止重试」的假设
2. 看失败轨迹 → `tools=0`：agent **一次工具都没调**就结束了，而且轨迹只有第 1 轮 → 说明**对话在第 2 轮就断了**
3. 查运行级异常 → 23/204 次 `Maximum number of retries (2) exceeded`
   （上游用 `openai.OpenAI()` 建客户端，SDK 默认 `max_retries=2`，限流后直接抛错）

**根因**：并行提速时没考虑端点的并发承受能力；而且**中断的运行被计成了任务失败**。

**修复**：
1. `CompatOAI` 给所有 API 调用套指数退避重试（限流/超时/连接抖动/5xx，最多 6 次）
2. 中断的运行标记 `aborted`，与"模型答错"**分开统计**（bench 打印 `[ABRT]`，analyze 排除并报数）
3. 默认并发降到 2

> **教训**：**基础设施故障必须与模型能力失败分开统计**，否则一次限流就能把整轮结论带偏。
> 这与之前"均值被离群值污染""中断当失败"是同一类错误的三个变体 ——
> **都是"统计口径没把非模型因素隔离出来"**。

### 5.1 v5 后的两项量化（此前从未做过）

**① 判分器灵敏度 —— 变异测试**

对每个任务�� gold 造一个**单点错误轨迹**（改故障类型 / 换错库存序列号 / 改退款金额 / 多加一张单），
判分器必须全部拒绝：

```
扰动样本 9 个 | 判分器未拒绝 0 个
```
→ DB 判分**无假阴性**（不存在"做错了却判对"）。

**② NL judge 的独立第二意见 —— 确定性正则交叉验证**

此前只人工核对了**失败运行**的 NL 判定，**成功运行是否有假阳性从未查过**。
用确定性正则独立核验 255 条可机械核对的断言（工单号 `TK\d{4}` / `24 小时` / 金额 / 欠费 / 过保 / 序列号）：

```
可机械核对的断言 255 条 | 一致 253 | 不一致 2 | → 逐条查证：2 条全是**我正则的假阴性**
   （客服写"保修已于 2024年6月1日到期"，我的正则要求出现"期"字）
```
→ **NL judge 实际一致率 100%**。

### 5.2 本轮修掉的方法论缺口

**B 变体相对 A 同时变了三件事**，此前从未拆开：

| 子机制 | 含义 | 此前是否单独测过 |
|---|---|---|
| **裁剪** | 只注入与本任务相关的规则 | ❌ |
| **要点化** | 规则呈现为要点列表而非长段落 | ❌ |
| **红线前置** | 红线规则集中置顶 | ❌ |

不拆开就无法回答「上下文工程里到底是哪一部分在起作用」——
这正是"方法还是手艺"这个问题的核心。已把三者做成**正交开关**
`render(spec, scenes, points, redline_first)`，并新增 `B_crop` / `B_points` 两个拆解变体。

### 5.3 统计判据也要跟着改

总体 pass^3 的粒度受限于任务数（1/17 = 0.059），**配对比较**（同一任务上逐对比）
的粒度是 1 个任务，灵敏得多。`scripts/analyze.py` 已新增配对差异指标。
