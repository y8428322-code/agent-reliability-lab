## 4. 三个结论

### 4.1 上下文工程是**决定性**的改进，且作用机制可被精确定位

| 指标 | A_baseline | B_context | 变化 |
|---|---|---|---|
| pass@1 | 0.843 | **0.941** | +0.098（+5 次运行） |
| **pass^3** | 0.765 | **0.941** | **+0.176（+9 次运行）** |
| 中位工具调用 | 4 | 3 | −25% |

pass^3 的提升（+0.176）**远大于** pass@1（+0.098）→ 提升的是**稳定性**：
A 的 pass^3 比自己的 pass@1 低 0.078（经常蒙对一次）；B 两者相等（3 次全过的比例最高）。

**决定性证据是 T01**：

| 变体 | 实际建单 | 结果 |
|---|---|---|
| A_baseline（原始 policy 全文） | 断网 + **电视信号**（2 张） | 3/3 全错 |
| B_context（结构化摘要） | 断网（1 张） | 3/3 全对 |

A 的轨迹里**明明提到电视会随宽带一并恢复**，却还是建了第二张单 ——
说明那条规则**就写在策略里**，但埋在中间的叙述段落中，模型**检索不到、也没应用**；
B 把策略改成「红线前置 + 分节 + 关键判据加粗」之后，同样的规则就能被检索和应用。

> **这正是上下文工程的作用点**：不是"规则写没写"，而是**能不能从长文本里检索到并应用**。
> 这也是本项目最值得写进简历的一条：**同样一份规则，改变呈现方式就改变了行为。**

### 4.2 反思（C）与基线**完全打平** —— 不损害，但也不增益

`C_reflection` = 0.941 / 0.941，与 `B_context` 逐任务逐项完全一致。

原因与方法本身的盲区有关：Reflexion 式反思记忆是**"待办清单"**性质的，
它问的是"还有什么没做"，天然偏向**补做**；而本任务集的主失败模式是**做多了**
（12 次失败里 11 次是"多执行了一个写操作"，0 次是"该做的没做"）。
反思里没有"你已经多做了一步"这个概念，自然无从纠正。

> **评估一个改进手段之前，先确认失败模式与该手段的作用方向是否匹配。**
> 主失败模式是"过度执行"时，需要的是**减法机制**（收紧可行域），而不是补做清单。

### 4.3 减法机制（D/E）**降低了错误写操作**，但**牺牲了稳定性**

| 变体 | DB 维度 | pass^3 | 失败归因 |
|---|---|---|---|
| B / C | 0.941 | 0.941 | 多换机 ×3（**过度执行**） |
| D | 0.941 | 0.882 | 少建单 ×2 + 多换机 ×1（**过度保守**） |
| E | **0.980** | 0.882 | 未闭环 ×2 + 多换机 ×1 |

- **E 的 DB 维度最高（0.980）**，失败几乎全是「未闭环」—— 说明减法机制**确实压住了不该做的写操作**，
  代价是把可做但没做的事也压掉了（过度保守）。
- **H9 从 0/3 改善到 1/3**（D 和 E 各一次成功，那次成功只建了单、没换机）—— 方向对，但**不稳定**。
- D 在 H10 掉到 2/3（参数错自恢复场景被过度保守的约束干扰）。

> 与 4.2 合并看：**凡是给 agent 增加运行时自由度或收紧其决策空间的做法，在本任务集上都没有净收益**——
> 反思不增益，减法不增稳。唯一有效的是**改变上下文的呈现方式**（4.1）。

## 5. 主失败模式随变体迁移

| 变体 | 主失败模式 | 含义 |
|---|---|---|
| A_baseline | **多建单**（找不到例外规则） | 上下文太长，规则检索不到 |
| B / C | **多换机**（过度执行） | 知道规则但仍然越界 |
| D | **少建单**（过度保守） | 约束太紧，把该做的也压掉了 |
| E | **未闭环**（做了但不告知到位） | 约束导致话术不完整 |

这条**迁移链本身就是一份诊断报告**：不同 agent 策略会**把失败推到不同的阶段**，
所以改进必须针对当前所处的阶段，而不是笼统地"让 agent 更小心"。

## 6. 评测床在本轮固化的三项判定约束

判分链路本身也是被测对象。本轮把三条判定约束固化进评测床：

| 约束 | 做法 | 为什么必要 |
|---|---|---|
| **gold 可由策略推导** | 每条任务的 gold 都能追溯到策略里的一条规则；策略没规定的事不判 | 否则判的是"策略没规定的事"，分数没有意义 |
| **状态哈希与写操作顺序无关** | 工单/退款在哈希里按业务字段排序（剔除自动分配的 id），重复项仍保留 | 否则同一组写操作换个顺序就被判失败 |
| **反思与 agent 同源** | 反思注入的策略与 agent 实际看到的策略由同一个 `policy_for_variant()` 提供 | 否则反思指向的条款 agent 根本不在意 |

另有两项判分可靠性保障：否定式断言的判定器用 4 个构造样例实测 **4/4 正确**；
失败归因统一以 **DB 的 `audit_log`**（被执行方自己写下的事实）为准，而不是从流式消息反推。

> 这条本身也是一条方法论：**判分与归因都应优先使用"被执行方自己记录的事实"，而不是从日志反推的推断。**

## 7. 局限（必须连同结论一起读）

1. **1 个模型、1 个域** → 结论**不可外推**
2. **17 任务 × 3 次** → pass@1 相差 0.098 ≈ 5 次运行；主要依据是 **pass^3**（相差 0.176 ≈ 9 次运行）
3. **NL 维度区分度弱**（0.961~0.980）→ 有效判分主要靠 DB 维度
4. **用户是脚本化的** → 不测"应对混乱用户"
5. **无外部分数对照** → 只做组内消融，不宣称绝对水平
6. 任务是自写的 → 但**判分逻辑与 agent 实现完全解耦**（gold 由参考轨迹独立回放得出）
