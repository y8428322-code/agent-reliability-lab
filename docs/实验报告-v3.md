## 3. 三个结论

### 3.1 唯一稳定有效的改进是**上下文工程**

`B_context` 相对 `A_baseline`：

| 指标 | A_baseline | B_context | 变化 |
|---|---|---|---|
| pass@1 | 0.896 | **0.938** | +0.042（+2 次运行） |
| **pass^3** | 0.812 | **0.938** | **+0.126（+6 次运行）** |
| 中位工具调用 | 4 | **3** | −25% |
| 平均工具调用 | 3.83 | **3.35** | −12.5% |

**pass^3 的差距（+0.126）远大于 pass@1（+0.042）**，说明上下文工程带来的不只是"偶尔对"，而是**更稳定地对**：
A_baseline 的 pass^3 (0.812) 比自己的 pass@1 (0.896) 低 0.084，说明它经常"蒙对一次"；
B_context 的 pass^3 **等于** pass@1 (0.938)，说明它 3 次全过的比例最高。

### 3.2 两类"让 agent 自省/自查"的机制，在本任务集上**都是净负收益**

| 变体 | 机制 | pass@1 | pass^3 | 修了谁 | 又弄坏了谁 |
|---|---|---|---|---|---|
| C_reflection | 单向反思（只问"还没做什么"） | 0.896 | 0.875 | — | **T01 3/3 → 1/3** |
| D_guarded | 减法机制（前置条件 + 动作边界） | 0.917 | 0.875 | T01 2/3 → 3/3 | T02 3/3 → 2/3；新增 1 次"未闭环" |
| E_guarded_reflect | 减法 + 双向反思 | 0.875 | **0.750** | T01 | T02、T03、T10；新增"未闭环"×2、"参数错"×1；1 次失控（137 次调用） |

**共同规律**：它们能修好**个别任务**，但同时**引入新的不稳定**——修好 T01 的同时把 T02/T03/T10 弄掉，
甚至新增了「未闭环」「参数错」这类之前没有的失败模式。净效果为负。

**原因分析（本报告最重要的一条）**：

> 反思与减法机制都在**运行时给 agent 增加了额外的自由度**：
> 反思多一次 LLM 调用 + 多一段注入上下文；减法多一条工具描述 + 一段系统约束。
> 当失败模式是「**漏做**」时，这些额外信息是有用的补充；
> 但当失败模式是「**多做**」时，它们反而成了**噪声放大器** ——
> agent 反复改、反复查，甚至陷入重复生成（本轮 E 出现 1 次 137 次工具调用的失控运行）。

**推论**：针对"过度执行"型失败，需要的不是"让 agent 更小心"，而是**收紧可行域** ——
把策略规则从 prompt 挪到**工具层的参数校验**里（例如：换机前必须已存在状态为"已完工"的故障工单）。
这类约束不增加运行时自由度，只减少可执行的动作集合。这属于 Phase 4。

### 3.3 H9 是**模型能力天花板**，不是变体问题

H9（用户同时说"宽带断了"+"光猫也坏了要换机"）在 **全部 5 个变体 × 3 次 = 15 次运行中全部失败**，
且失败归因一致（`多换机 x1`）。补跑验证（E 变体，H9 再跑 3 次）同样 0/3。

模型的理解始终是「按顺序都办」，而不是策略要求的「一次只办一个、其余等确认」。
**这是当前模型的能力上限，任何 prompt 层面的手段都无法纠正。**

## 4. 加固项（Phase 4 前置）

本轮同时做了三处加固，并在补跑中验证：

| 加固 | 原因 | 验证 |
|---|---|---|
| **参数修复**（`compat.repair_args`）：从被上游拼接坏的参数里取最后一个完整 JSON 对象 | 上游 `_chat_stream` 用 `+=` 累加参数，假定服务**分片**返回；若服务每个 chunk 都返回**完整**参数，累计结果变成 `{"a":1}{"a":1}...`，工具报 `Parameters must be formatted as a valid JSON!` | 已实现，构造 `CompatAssistant` 覆写 `_call_tool` |
| **失控运行标记**（单轮 >15 次工具调用即标记） | 一次 137 次调用的离群运行会把均值从 3.3 拉到 5.8，污染统计 | 已实现；分析脚本改为**中位数 + 失控计数**并列 |
| **归因数据源改用 DB 的 `audit_log`** | 从流式消息反推的调用列表会因参数格式差异重复计数（曾误报"多换机 x2"） | 已实现，归因与 audit_log 完全一致 |

**补跑验证**（E 变体，H2 + H9，各 3 次）：
```
H2  3/3 全部通过，工具调用稳定 7 次（不再出现 137 次失控）
H9  0/3 全部失败，归因一致「状态不符(多换机 x1)」
```
→ 证实：**失控是偶发的模型退化，H9 的失败是系统性的**。

## 5. 局限（必须连同结论一起读）

1. **1 个模型、1 个域** → 结论**不可外推**到其他模型或场景
2. **16 任务 × 3 次** → pass@1 的 0.042 差距只相当于 2 次运行，**单看 pass@1 不足以判定**；
   本报告的主要依据是 **pass^3**（差距 0.126 ≈ 6 次运行）与**逐任务稳定性**
3. **NL 维度区分度仍弱**（0.969~0.986）—— 本轮新增的否定式断言让它从"恒 1.000"变成有变化，但主要判分仍靠 DB 维度
4. **用户是脚本化的** → 不测"应对混乱用户"
5. **无外部分数对照** → 只做组内消融，**不宣称绝对水平**
6. 任务是自写的 → 判分逻辑与 agent 实现完全解耦（gold 由参考轨迹独立回放得出）
